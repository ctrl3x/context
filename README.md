# Как медиа искажают исследования — порядок работы с ИИ-агентом

Учебный проект НИУ ВШЭ: одностраничный лендинг-скроллтеллинг (`index.html`) и его мобильная версия (`mobile.html`). Техническая часть описана в `AGENTS.md`; этот README — о процессе разработки с ИИ-агентом.

## 1. Общая схема

Проект разрабатывался в паре «человек — ИИ-агент»:

- **Человек** ставит задачи, принимает/отвергает предложения агента, проверяет результат визуально и принимает решение о коммите.
- **ИИ-агент** читает проектный контекст (`AGENTS.md`, `LOG.md`, код), вносит правки, проводит проверки в headless-браузере и ведёт журнал решений.

Агент не «генерирует сайт по описанию», а работает внутри уже существующей хрупкой кодовой базы: пороги пинов, границы зон перехвата колеса и fallback-ветки завязаны друг на друга, поэтому правки выполняются по правилам `AGENTS.md` («минимальные правки») и завершаются записью в `LOG.md`.

## 2. Инструментальная среда: OpenCode

Основной инструмент — [OpenCode](https://opencode.ai): агентный каркас, запускающий LLM-агента поверх локального репозитория. Использовались:

- **Сессии** — каждая содержательная задача отдельная сессией («Добавление скролл-переходов», «Мобильная адаптация макета Figma» и др.); по проекту проведено 12 сессий.
- **Встроенные агенты** — основной `build` выполняет правки; субагент `@explore` вызывался для поисковых задач (например, поиск узла вердикт-экрана в дампе Figma) в собственном контексте.
- **Инструменты** — чтение/поиск/правка файлов, shell (локальный сервер, headless Chrome), вопросы пользователю.
- **Контекст проекта** — `AGENTS.md` из корня автоматически подставляется в контекст агента каждой сессии.

### Модель

Все сессии выполнены на модели **`aiacademy/aiacademy-coder`**; другие модели не использовались.

## 3. MCP-сервер Figma

К агенту подключён **MCP-сервер Figma** (Model Context Protocol — протокол доступа агента к внешним инструментам). Через него агент работал напрямую с исходным макетом: `get_metadata`/`get_document` (навигация по слоям), `get_design_context` (узлы с координатами, шрифтами, цветами), `get_selection`, `get_variable_defs`.

Применение:

1. **Источник координат и текстов.** Позиции элементов заданы в координатах макета (часто inline-style): десктоп — по узлам (мокапы 1779:928, 1982:808/847/894/945), мобильная версия — по мокапу 1972:766.
2. **Структурированные выгрузки** сохранены в репозитории (`proof/mobile-1972-766.json`, `proof/mobile-spec.txt`) — эталон координат/текстов при последующих правках.
3. **Согласование с дизайнером.** При пересборке слоя в Figma агент выкачивал узел по идентификатору заново и переносил изменения в код.
4. **Типографика по макету** — line-height/top вычислялись из тайп-баундов Figma и верифицировались canvas-метриками в headless Chrome.

## 4. `AGENTS.md` — контракт проекта

`AGENTS.md` — файл инструкций, автоматически включаемый агентской средой в контекст агента. Он выполняет роль технического паспорта и регламента:

- описание проекта, запуск, структура репозитория;
- ключевые концепции (дизайн-канва 1280×832, `scale()`, пины, перехват wheel/keydown, preview-хэши);
- конвенции (язык комментариев «почему», нейминг, палитра из CSS-переменных, синхронизация текстов десктоп/мобайл);
- правила работы агента — минимальные правки, чтение `LOG.md` до правки и дополнение после, запрет сборки/зависимостей, запрет трогать референсы.

Новое общее правило проекта сначала формулируется в `AGENTS.md`.

## 5. `LOG.md` — журнал решений

`LOG.md` хранит «почему так»: происхождение магических чисел и **отвергнутые варианты**. Git показывает, что сделано, но не почему именно так — без этого осознанное решение через месяц откатили бы как случайное.

Формат записи жёстко ограничен (≤5 строк): *что / почему / отвергнуто / файлы*. Пример:

> **tdgates: первый стык в sci-flat глушится флагом.** Что: `flat()` отключает все 4 ветки стыка. Почему: пыль округления при дробном scale оставляла up-зону живой на стоянке разбора. Отвергнуто: подгонка арифметики зон — ломает симметрию возврата. Файлы: `js/tdgates.js`.

Правила ведения: запись после каждого значимого изменения, новые сверху; когда вывод стал общим правилом — он переезжает в `AGENTS.md` или комментарий в коде; потолок ~20–30 записей, история — в git.

## 6. Типовой цикл работы над задачей

1. **Постановка** — человек описывает задачу, часто с указанием узла макета Figma.
2. **Контекст** — агент читает `AGENTS.md` (автоматически) и записи `LOG.md` по затронутым секциям.
3. **Диагностика** — при необходимости замеры в headless Chrome (`tmp/cdp_*.mjs`, числовые проверки через dump-dom).
4. **Правка** — минимальные изменения по конвенциям.
5. **Верификация** — headless-прогоны сценариев + визуальная проверка человеком.
6. **Журнал** — запись в `LOG.md`; новое общее правило — в `AGENTS.md`.
7. **Коммит** — решение принимает человек; выжимка решений остаётся в `LOG.md`.

## 7. Контроль качества

- Все решения о дизайне и текстах — за человеком; текстовые правки всегда синхронно в обеих версиях (`index.html` / `mobile.html`).
- Каждое неочевидное число в коде должно быть объяснимо — комментарием «почему» или записью `LOG.md`; это основной фильтр качества.
- Отвергнутые варианты фиксируются явно — будущие сессии не предлагают их повторно.
- Долгоживущие знания мигрируют: `LOG.md` → комментарий в коде → `AGENTS.md`.
